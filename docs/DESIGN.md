# Craftflow — дизайн-документ

> Рабочее название проекта — **Craftflow**. Переименование = замена в этом файле, `CLAUDE.md` и `Cargo.toml`.

## 1. Концепция

Десктопный инструмент для планирования производственных цепочек в Minecraft (ванилла и моды), в духе Satisfactory Modeler. Рецепты, машины и механики модов подключаются через **паки данных** и **плагины**; ядро ничего не знает о конкретных модах.

Пользователь либо собирает схему завода на нодовом графе, либо задаёт целевой выход, а приложение считает потоки, количество машин, энергию/стресс и находит узкие места.

### Сценарии
- **«Сколько нужно?»** — цель (N предметов в минуту или партия из N штук) → машины, сырьё, энергия.
- **«Где тормозит?»** — нарисованная схема → загрузка машин, дефициты, излишки, бутылочные горлышки.
- **«Покажи другу»** — файл схемы или строка для шаринга.
- **«Что закодировать в ME?»** — чек-лист шаблонов AE2 для плана.

### Целевая аудитория и первая цель
Игроки в большие модпаки. Первая целевая сборка — **ATM10** (NeoForge). Первые моды: ванилла, Mekanism, Create, AE2 (все с аддонами из ATM10). Кандидат следом — Productive Bees.

### Нефункциональные требования
- Кроссплатформенность: Linux, Windows, macOS с первого дня (CI собирает и тестирует под все три).
- Быстрый отклик: пересчёт схемы из сотен нод — миллисекунды, на каждое изменение.
- Расширяемость: сторонние разработчики добавляют моды без изменения ядра.
- Приложение читает ассеты модов из локальной установки пользователя и **ничего не распространяет**.

## 3. Архитектура

### Принципы
1. **Ядро не знает о модах.** Даже ванилла — встроенный плагин + пак.
2. **GUI — тонкая оболочка.** Вся логика в библиотечных крейтах, тестируется без окна.
3. **Есть CLI**, умеющий всё, что нужно для проверки логики без GUI: импорт, загрузку паков, расчёт схемы из файла.
4. **Единственный примитив солвера — Process** (см. 6.3). Любая нода, в том числе плагинная, сводится к набору процессов.
5. Внутренние единицы — **в тик** (20 тиков = 1 с), `f64`. Пользователю — /с, /мин, /ч на выбор.

### Структура workspace

```
craftflow/
├── Cargo.toml                # workspace
├── CLAUDE.md
├── docs/
│   ├── DESIGN.md
│   └── ROADMAP.md
├── crates/
│   ├── model/      # типы данных: Resource, Tag, Machine, Recipe, Pattern, Pack-манифест, единицы
│   ├── expr/       # движок формул: парсинг, компиляция, вычисление с переменными
│   ├── packs/      # загрузка паков, реестр, зависимости, оверлеи, валидация
│   ├── graph/      # схема: ноды, порты, связи, сети; формат файла, версии, миграции, строка шаринга
│   ├── solver/     # сведение схемы к процессам, LP, режимы анализа/плана/партии
│   ├── import/     # чтение JAR: рецепты, lang, текстуры; диспетчеризация к импортёрам плагинов
│   ├── plugin/     # хост Luau: песочница, API, манифесты, жизненный цикл
│   ├── icons/      # атлас иконок, кэш, (позже) изометрический рендер блоков
│   ├── app/        # eframe-приложение
│   └── cli/        # headless-утилита
├── plugins/        # встроенные плагины (Luau + паки)
│   ├── vanilla/
│   ├── mekanism/
│   ├── create/
│   └── ae2/
└── tests/
    └── scenarios/  # эталонные сценарии (раздел 11)
```

**Доступ к данным паков.** `graph` и `solver` должны читать рецепты и машины, но по графу зависимостей они не выше `packs`. Поэтому в `model` объявлен трейт `Catalog` (поиск ресурса, тега, машины, рецепта и вычисление формулы машины), а `packs::Registry` его реализует. Формулы отдаются через `evaluate`, возвращающий число, а не скомпилированное выражение: тип выражения принадлежит `expr`, от которого `model` не зависит.

Зависимости крейтов (стрелка = «зависит от»):
`app → solver, graph, packs, plugin, icons, import`; `cli → то же без icons/app`; `solver → graph, model, expr`; `graph → model`; `packs → model, expr`; `import → model, plugin`; `plugin → model`.

## 4. Модель данных

Все сущности адресуются строковыми ID вида `namespace:path` (как в Minecraft): `minecraft:iron_ingot`, `mekanism:enrichment_chamber`.

### 4.1 Resource
То, что течёт по графу.

```json
{ "id": "minecraft:iron_ingot", "kind": "item", "name_key": "item.minecraft.iron_ingot", "icon": "minecraft:item/iron_ingot" }
```

`kind`: `item` | `fluid` | `energy` | `stress` | `custom:<plugin>/<name>`.
Единица хранения: item — штуки, fluid — mB, energy — единица из определения ресурса (`FE`, `J` …), stress — SU.
Необязательное поле `unit` задаёт эту единицу для `energy` (`"unit": "FE"`); для остальных видов единица подразумевается видом.

### 4.2 Tag
Группа взаимозаменяемых ресурсов: `#c:ingots/iron` → список ID. Вход рецепта может быть тегом; конкретный ресурс выбирается в схеме или солвером.

### 4.3 Machine
```json
{
  "id": "mekanism:enrichment_chamber",
  "categories": ["mekanism:enriching"],
  "params": {
    "speed_upgrades":  { "type": "int",  "min": 0, "max": 8, "default": 0 },
    "energy_upgrades": { "type": "int",  "min": 0, "max": 8, "default": 0 }
  },
  "formulas": {
    "duration": "recipe.duration * speed_factor(speed_upgrades)",
    "energy_per_tick": "base_energy * energy_factor(speed_upgrades, energy_upgrades)"
  },
  "constants": { "base_energy": 50 },
  "networks": { "energy": "mekanism:joules" },
  "accuracy": "exact"
}
```
(Числа иллюстративные.) `params` — переменные, которые пользователь крутит в инспекторе.
Тип параметра (`type`) — `int`, `float` или `bool`; `min` и `max` необязательны и к `bool` не применяются. В формулах значение любого типа приходит как `f64`, `bool` — как `0` или `1`. `formulas` — выражения от параметров, констант и полей рецепта. Функции вроде `speed_factor` объявляются в паке как именованные выражения или плагином.

### 4.4 Recipe
```json
{
  "id": "mekanism:enriching/iron_ore",
  "category": "mekanism:enriching",
  "duration": 200,
  "inputs":  [ { "resource": "#c:ores/iron", "amount": 1 } ],
  "outputs": [ { "resource": "mekanism:dust_iron", "amount": 2 },
               { "resource": "some:byproduct", "amount": 1, "chance": 0.25 } ],
  "catalysts": [],
  "accuracy": "exact"
}
```
- `chance` → в расчётах матожидание; поле необязательное, по умолчанию `1.0` (выход гарантирован).
- `catalysts` — нужны, но не расходуются (`{"resource": ..., "amount": 1}`). Если предмет расходуется и возвращается, это обычные вход + выход.
- `duration` в тиках; итоговая длительность определяется формулой машины.

### 4.5 Source
Добыча без рецепта (ферма, генератор булыжника, бесконечная вода). Это Machine без входов, рецепт которой задаёт скорость. Отметка `accuracy: "estimated"` для всего, что зависит от механики мира.

### 4.6 Отметка точности
Любое числовое значение (рецепт, машина, константа) может иметь `accuracy: "exact" | "estimated"`. Результат расчёта, в который вошла оценочная величина, помечается в UI.

### 4.7 Pattern (AE2 и подобное)
Шаблон — **отдельная от рецепта** сущность: что сеть отправляет и что ждёт обратно.

```json
{
  "id": "user:netherite_sword_upgrade",
  "kind": "processing",
  "sends":   [ { "resource": "minecraft:diamond_sword", "amount": 1 },
               { "resource": "minecraft:netherite_ingot", "amount": 1 },
               { "resource": "minecraft:netherite_upgrade_smithing_template", "amount": 1 } ],
  "expects": [ { "resource": "minecraft:netherite_sword", "amount": 1 },
               { "resource": "minecraft:netherite_upgrade_smithing_template", "amount": 1 } ],
  "target": { "node": "<node-id>" }
}
```
`kind`: `crafting` (исполняется ассемблером внутри ME-ноды) | `processing` (привязан к ноде схемы). Ядро хранит шаблоны как обобщённую сущность; семантику даёт плагин (AE2).

**Валидация:** солвер сравнивает `expects` с тем, что реально выдаёт целевая нода на те же входы. Расхождение — ошибка на схеме («шаблон ждёт обратно кузнечный шаблон, а установка его расходует»).

## 5. Паки данных

Пак — каталог или zip:

```
mekanism-atm10/
├── pack.toml
├── resources.json
├── tags.json
├── machines.json
├── functions.json      # именованные выражения
├── recipes/*.json
└── overlays/*.json     # правки поверх других паков
```

```toml
[pack]
id = "mekanism"
version = "0.1.0"
format_version = 1
minecraft = "1.21.1"
loader = "neoforge"
depends = ["vanilla >= 0.1"]
```

**Файлы сущностей.** `resources.json`, `tags.json`, `machines.json` и каждый файл в `recipes/` содержат либо одну сущность, либо массив сущностей. Ключ — поле `id`. Подкаталоги в `recipes/` разрешены и читаются рекурсивно. Для единообразия любой вид можно разложить и по каталогу: `resources/`, `tags/`, `machines/`.

**`functions.json`** — словарь имени в параметры и тело:

```json
{
  "speed_factor": { "params": ["n"], "body": "1 / (1 + n * 0.5)" }
}
```

Тело — выражение движка формул. Функции могут ссылаться друг на друга независимо от порядка объявления. Тело видит **только свои параметры**: константы пака в нём недоступны, их передают аргументом. Имя, совпадающее со встроенной функцией или с функцией другого пака, перекрывает её по общему правилу слоёв.

**Язык формул.** Числа (`2`, `2.5`, `1e-3`), переменные (`speed_upgrades`, `recipe.duration` — точка часть имени, а не обращение к полю), `+ - * / % ^` (`^` правоассоциативен), сравнения `< <= > >= == !=` (дают `1` или `0`, равенство с эпсилоном), логика `&& || !` с коротким замыканием (ноль — ложь), условие `cond ? a : b`, вызовы функций. Всё считается в `f64`. Встроенные функции: `abs`, `floor`, `ceil`, `round`, `sqrt`, `exp`, `ln`, `log10`, `pow`, `min`, `max`, `clamp`.

Формула машины может читать свои `params`, свои `constants` и поля рецепта (пока только `recipe.duration`). Любое другое имя — ошибка валидации пака.

**Зависимости.** `depends` — список строк вида `vanilla >= 0.1`; требование в синтаксисе Cargo, без требования — любая версия. Версия самого пака — полная `major.minor.patch`. Пак всегда применяется после тех, от кого зависит; цикл зависимостей — ошибка загрузки.

**Слои данных** (позже перекрывает раньше): встроенные паки → импортированные из JAR → ручные оверлеи → пользовательский пак. Сущность с тем же `id` замещает предыдущую целиком.

**Оверлеи** (`overlays/*.json`) — точечные правки поверх уже загруженных сущностей, в том числе чужих. Файл содержит список операций:

```json
{
  "operations": [
    { "op": "set",    "target": "machine:mekanism:enrichment_chamber",
                      "path": "constants.base_energy", "value": 60 },
    { "op": "set",    "target": "recipe:minecraft:smelting/glass",
                      "path": "outputs.0.amount", "value": 2 },
    { "op": "remove", "target": "recipe:minecraft:smelting/stone" },
    { "op": "remove", "target": "machine:minecraft:furnace", "path": "constants.coal_burn_time" },
    { "op": "add",    "kind": "resource", "value": { "id": "user:scrap", "kind": "item" } }
  ]
}
```

- `target` — `<kind>:<namespace>:<path>`, где `kind` ∈ `resource`, `tag`, `machine`, `recipe`.
- `path` — путь через точку внутри сущности. Числовой сегмент индексирует массив (`outputs.0.amount`). Недостающие объекты по пути создаются; выход за границу массива — ошибка.
- `remove` без `path` удаляет сущность целиком, с `path` — одно поле. Удаление того, чего нет, ошибкой не считается.
- `add` требует `kind` и `value` с полем `id`.
- `set` и `remove` по несуществующей сущности — ошибка валидации (вероятнее всего опечатка или пак обновился).

Операции применяются к «сырому» JSON до превращения в типы модели — поэтому правка одного числа не требует переписывать сущность целиком.

**Валидация** после слияния: ссылки рецептов на ресурсы и теги, значения тегов, выход-тег (запрещён), неположительные количества и длительности, `chance` вне `0..=1`, компиляция формул машин и их переменные. Категория без машин или машина без рецептов — предупреждение, а не ошибка: так выглядит частичный пак.

**Пользовательский пак** — редактируется прямо в UI: свои рецепты, свои машины («установки»), правки значений. При шаринге схемы используемые пользовательские сущности встраиваются в неё.

## 6. Граф (схема)

### 6.1 Типы нод в ядре
| Нода | Назначение |
|---|---|
| Machine | машина + рецепт + параметры + количество |
| Source | вход без рецепта, скорость или «бесконечно» |
| Output | цель/потребитель; лишнее отображается как излишек |
| Hub | смешивание многих входов/выходов (сундук, ME-сеть) |
| Group | *(позже)* свёрнутый подграф с внешними портами, блюпринт |
| Note | комментарий |

Плагины регистрируют свои типы нод (ME-сеть, вал Create и т.п.).

### 6.2 Порты, связи, сети
- Порт типизирован ресурсом или тегом. Связь несёт один ресурс.
- **Порты неявные.** Связь — это `{from, to, resource}`; отдельных идентификаторов портов нет, у машины набор портов выводится из рецепта. Поэтому смена рецепта у ноды не ломает ссылки, а оставляет связь, несущую ресурс, которого нода больше не касается, — это ловит валидатор. Если для плагинной ноды понадобятся два разных порта с одним ресурсом, в связь добавится необязательное поле `port`; файлы v1 от этого не сломаются.
- К порту можно подключить несколько связей; распределение считает солвер. Сплиттеров/мерджеров нет.
- Связь по умолчанию безлимитная. Опционально — тип транспорта (от плагина) с пропускной способностью.
- **Сети** для `energy` и `stress`: машина привязывается к именованной сети, а не соединяется линией. Сеть показывает баланс генерации и потребления. Линии энергии рисовать можно, это то же самое.
- Нагрузка машины на сеть берётся из формулы **`<роль>_per_tick`**: машина на роли `energy` читается из `energy_per_tick`, на роли `fuel` — из `fuel_per_tick`. Значение — на одну работающую машину за тик; отрицательное означает, что машина генерирует. Баланс сети **показывается, но не ограничивает** решение: схема, в которой генераторы ещё не нарисованы, должна считаться, а не выдавать нули.

### 6.3 Process — примитив солвера
Каждая нода сводится к одному или нескольким процессам:

```
Process {
  inputs:  [(resource, amount_per_activity)],
  outputs: [(resource, amount_per_activity)],
  activity_bounds: [min, max],   # например, 0..(кол-во машин × скорость)
  cost_terms: [...],             # для оптимизации
}
```
Machine → процесс рецепта с учётом формул; Source → процесс без входов; Hub → балансы. Плагинная нода возвращает процессы из Luau. **Ограничения обязаны быть линейными** — это контракт API.

### 6.4 Режим анализа
Переменные: активность процессов, потоки по связям. Ограничения: баланс каждого ресурса в каждой ноде, лимиты источников/связей/машин. Цель: максимизировать выход на Output. Циклы разрешены.

Вывод: поток по каждой связи, загрузка машины в %, цвет (зелёный — сбалансировано, жёлтый — недогружена, красный — горлышко), панель излишков/дефицитов, баланс сетей, предупреждения о `estimated`.

## 7. Калькулятор

**Вход:** цели, доступное сырьё (с лимитами и весами), предпочтения рецептов, режим.

**Выбор рецептов:**
1. Предпочтения: глобальные («предпочитать Mekanism», «без Create») и на предмет. Хранятся в профиле.
2. Авто-оптимизация: минимизация стоимости — сырьё с весами, число машин, энергия. Веса настраиваются.

**Режимы:**
- **Поток** — N в единицу времени постоянно.
- **Партия** — N штук: итог сырья и промежуточных. *(Позже: время выполнения с учётом зависимостей.)*

**Количество машин:** LP даёт дробное → показываем округление вверх и реальную загрузку. *(Позже: режим целых машин через MILP.)*

**Побочка** — выход-излишек с действием «пустить в переработку».

**Результат — граф** с автоматической послойной раскладкой (сырьё слева, цель справа), открывается в редакторе для правки. Для планов с ME — чек-лист шаблонов.

## 8. Плагины (Luau)

### 8.1 Манифест
```toml
[plugin]
id = "mekanism"
version = "0.1.0"
api_version = 1
depends = ["vanilla >= 0.1"]
entry = "init.luau"
packs = ["packs/mekanism"]
```

### 8.2 Точки расширения (API v1)
```lua
return function(api)
  api.register_recipe_importer("mekanism:enriching", function(json) return { --[[recipes]] } end)
  api.register_function("speed_factor", function(n) return ... end)   -- доступно формулам
  api.register_node_type({ id = "ae2:me_network", ports = ..., params = ..., processes = function(node) ... end })
  api.register_transport({ id = "mekanism:pipe_elite", resource_kind = "item", capacity_per_tick = ... })
  api.register_network_kind({ id = "create:kinetic", resource_kind = "stress" })
  api.register_validator(function(schema) return { --[[issues]] } end)
end
```
- Функции, вызываемые из формул, должны быть чистыми; движок может кэшировать результаты.
- `processes` вызывается при изменении ноды, не на каждой итерации солвера.

### 8.3 Песочница
Нет доступа к ФС, сети, `os`, `io`, `require` вне каталога плагина. Лимиты памяти и времени исполнения. Ошибка плагина не роняет приложение — плагин отключается с сообщением.

### 8.4 Будущее
WASM-плагины (через `extism`) для тяжёлой логики на любых языках — не в MVP.

## 9. Импорт данных

1. **Из JAR** в папке `mods/` выбранного инстанса: `data/<ns>/recipe/**/*.json` → импортёр плагина по `type`; `assets/<ns>/lang/{en_us,ru_ru}.json` → названия; `assets/<ns>/textures/item/*.png` → иконки предметов. Неизвестные типы рецептов — в отчёт импорта, не ошибка.
2. **Ручной оверлей**: параметры машин (скорости, энергия, апгрейды), которых нет в JSON-рецептах.
3. *(Позже)* **Мод-экспортёр** под NeoForge: дамп всех рецептов после загрузки модпака (с правками KubeJS) и рендер иконок.

Результат импорта кэшируется по хэшу набора JAR; повторный запуск быстрый.

**Иконки блоков:** сначала простой изометрический рендер кубических моделей из текстур; сложные модели — позже через мод-экспортёр. До этого — заглушка с текстурой.

## 10. Сохранение и шаринг

- **Файл схемы** — JSON с `format_version`, графом, параметрами, шаблонами, встроенными пользовательскими сущностями и **списком паков с версиями**.

```json
{
  "format_version": 1,
  "packs": [ { "id": "vanilla", "version": "0.1.0" } ],
  "nodes": [
    { "id": "ore", "type": "source", "resource": "minecraft:iron_ore",
      "rate": { "amount": 600, "unit": "minute" } },
    { "id": "furnaces", "type": "machine",
      "machine": "minecraft:furnace",
      "recipe": "minecraft:smelting/iron_ingot_from_ore",
      "params": { "speed_upgrades": 2 },
      "count": 8,
      "networks": { "fuel": "main" },
      "position": [120.0, 40.0] },
    { "id": "ingots", "type": "output", "resource": "minecraft:iron_ingot",
      "target": { "amount": 600, "unit": "minute" } },
    { "id": "chest", "type": "hub" },
    { "id": "n1", "type": "note", "text": "узкое место тут" }
  ],
  "links": [
    { "from": "ore", "to": "furnaces", "resource": "minecraft:iron_ore" },
    { "from": "furnaces", "to": "ingots", "resource": "minecraft:iron_ingot",
      "capacity": { "amount": 1200, "unit": "minute" } }
  ],
  "networks": { "main": { "kind": "vanilla:burn_time" } },
  "patterns": []
}
```

- `id` ноды — произвольная строка, уникальная в пределах файла (не `namespace:path`): её генерирует редактор.
- **Потоки** (`rate`, `target`, `capacity`) записываются как `{amount, unit}`, где `unit` ∈ `tick`, `second`, `minute`, `hour`. Без `unit` — в минуту. Внутри ядра всё переводится в тик (правило 4); файл человек читает и правит руками, поэтому единица в нём названа явно.
- `count` у машины — **верхняя граница**: сколько машин стоит. Без него солвер волен взять сколько угодно.
- `target` у Output — **потолок спроса**: солвер максимизирует выход, но не выше цели; недостижение показывается дефицитом, а не «задача нерешаема».
- `rate` у Source без значения — неограниченный источник.
- `networks` в ноде — роль (`energy`, `fuel`) к имени сети из `networks` схемы; вид сети должен совпасть с тем, что объявила машина.
- `position` хранится, чтобы раскладка холста переживала сохранение.
- Пустые коллекции в файл не пишутся.
- При открытии — проверка паков: отсутствующие/другие версии показываются, недостающие сущности подсвечиваются на холсте.
- **Строка шаринга** — сжатый (deflate) JSON в base64 с префиксом версии, в стиле чертежей Factorio.
- **Миграции** — цепочка `vN → vN+1`, тест на каждую. Файл поднимается до текущей версии на уровне JSON, до разбора в типы, поэтому разбирающий код всегда видит только актуальную форму. Версия выше поддерживаемой — ошибка с предложением обновить Craftflow, а не попытка угадать.
- *(Далеко потом)* онлайн-галерея.

## 11. Эталонные сценарии

Каждый — интеграционный тест в `tests/scenarios/` (схема + ожидаемые числа) и ручной сценарий в UI.

Каталог сценария: `schema.json`, `expected.json` и необязательный `pack/` — собственный пак, если сценарию нужны сущности, которых нет во встроенных. В `expected.json` перечисляются только те величины, которые сценарий проверяет (`outputs`, `loads`, `sources`, `links`, `networks`, `surplus`, `accuracy`), в единице из поля `unit`. `surplus` сверяется целиком: пустой объект значит «нигде ничего не копится». Добавление сценария — это добавление каталога, менять Rust не нужно.

1. **Ванилла: печи.** Железная руда → слитки в N печах, топливо. Проверка единиц и загрузки.
2. **Mekanism: обработка руды** с апгрейдами скорости. Проверка формул и энергосети.
3. **Create: дробление** с RPM и стрессом. Проверка кинетической сети и зависимости скорости от RPM.
4. **Цикл побочки.** Схема с возвратом побочного продукта на вход. Солвер сходится, излишки корректны.
5. **AE2: незеритовое улучшение.** Пользовательская установка (кузнечный стол, автоматизированный игроком) + шаблон обработки, отправляющий предмет, слиток и кузнечный шаблон и ожидающий обратно предмет и кузнечный шаблон + отдельный цикл размножения кузнечного шаблона. Проверки: схема воспроизводится полностью средствами UI; валидатор ловит ошибку, если установка не возвращает кузнечный шаблон; чек-лист шаблонов содержит оба шаблона.
6. **Калькулятор с выбором рецептов.** Цель с несколькими путями производства; предпочтения и авто-оптимизация дают разные корректные планы.
7. *(С плагином пчёл)* **Улей → центрифуга** с `estimated`-значениями и пометкой в UI.

- **Браузер:** поиск по названию/ID/моду, иконки, «где производится / где используется» (как в JEI/EMI); перетаскивание на холст создаёт ноду.
- **Холст:** ноды с иконкой, количеством машин, загрузкой; связи с потоком; цвета состояния.
- **Инспектор:** машина, рецепт (с выбором альтернатив), параметры (слайдеры), количество, сеть, итоговые потоки, отметки `estimated`.
- **Нижняя панель:** вкладки баланса ресурсов, сетей, чек-листа шаблонов, списка проблем (клик → нода на холсте).
- **Калькулятор:** форма целей, сырья, предпочтений → «Построить» → граф в редакторе.
- **Палитра команд** (Ctrl+K): добавить ноду, найти предмет, переключить единицы.
- **Редактор пользовательских рецептов и машин** — диалог.
- Тёмная и светлая темы, ru/en, undo/redo.
